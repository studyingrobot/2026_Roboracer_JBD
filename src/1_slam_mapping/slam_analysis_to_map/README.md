# slam_toolbox 오도메트리 오차 분석 -> bag 재생 전에 띄우면 됨 

f1tenth 차량 bag을 slam_toolbox로 돌릴 때, 오도메트리 오차를
**계통 성분(캘리브레이션)** 과 **비계통 성분(슬립·동역학)** 으로 분리한다.

## 원리

`map -> odom` 은 SLAM이 오도메트리에 가하는 **총 보정량**이다.

- 매끄럽게 변함 → 프론트엔드 (스캔 매칭이 매 키프레임 보정)
- 툭 점프      → 백엔드 (루프 클로저 후 그래프 재최적화)
- 단조 증가 추세 → 계통 오차 (wheelbase / 조향 게인)
- 추세 주변 진동 → 비계통 오차 (타이어 슬립)

## 사용법

로거는 **bag 재생과 실주행 둘 다** 된다. `/clock` 발행자가 있는지 보고
`use_sim_time` 을 자동으로 잡으므로 플래그를 줄 필요가 없다. 시작할 때
`use_sim_time=... (bag replay | live run)` 이 찍히니 맞는지만 확인할 것.

5초마다 추세·진동을 실시간으로 출력한다. 대회장처럼 시간이 없을 때는
CSV 분석까지 안 가고 이 줄만 봐도 판단이 된다.

```
t=  35.0s  mo_yaw= +15.20deg  trend=+0.746deg/s  osc_rms= 9.20deg  peak=37.10deg  rows=1300
```

- `trend` 이 0에서 유의미하게 벗어남 → 계통 오차. wheelbase / 조향 게인
- `osc_rms` 가 큼 → 슬립. 노면이 바뀌면 이 값이 바뀐다

bag이면 **재생 직전에**, 실주행이면 **출발 직전에** 띄운다. 노트북에서
실행하면 된다 (DDS로 차량 TF를 받으므로 차량에 올릴 필요 없음).

```bash
cd ~/2026_Roboracer_JBD/slam_analysis_to_map
python3 map_odom_log.py run2.csv base_link
```

세 번째 인자는 base 프레임 이름. `base_footprint` 를 쓰면 그쪽으로 바꾼다
(`ros2 run tf2_tools view_frames` 로 확인).

차량 컨테이너에서 재생:

```bash
ros2 launch offline_launch.py
ros2 bag play <bag> --clock -r 0.3
```

끝나면 Ctrl+C 후 분석:

```bash
python3 analyze2.py run2.csv     # 판단에 필요한 숫자는 여기 다 있다
```

`analyze2.py` 하나면 충분하다. `analyze.py` 는 점프 전체 목록과
5초 간격 궤적 표가 필요할 때만 (특정 시점을 파고들 때) 돌린다.

```bash
python3 analyze.py run2.csv
```

## run1.csv 결과 (2026-08-06 녹화본)

76.7초 / 3랩 / 랩당 21.4초.

| 항목 | 값 |
|---|---|
| map->odom 최종 | 이동 3.30 m, 회전 50.1도 |
| 추세 (계통) | +0.746 deg/s, 전 구간 +57도 |
| 진동 (비계통) | rms 9.2도, 최대 37.1도 |
| 누적 헤딩 odom | 1043.6도 (참값 1080도) |
| yaw 스케일 오차 | 약 4.6% 과소 추정 |

최대 보정 순간: t=59.50s (-20.8도), t=37.86s (-15.5도), t=45.00s (+13.7도).
t=57~60초 구간에서 74도까지 튀었다가 43도로 복귀 — 맵 좌상단 번짐의 원인.

**결론**: 계통 성분은 랩당 약 17도, 비계통 성분은 최대 37도.
비계통 쪽이 더 크므로 스케일 보정만으로는 부족하고 IMU 융합이 필요하다.

## 조치 우선순위

1. VESC `wheelbase` 를 약 4.5% 줄이거나 조향 게인을 4.5% 키운다 (계통 성분)
2. `/sensors/imu` + robot_localization EKF 융합 (비계통 성분) — 실제 개선폭이 큼
3. 그래도 남으면 slam_toolbox `minimum_travel_*` 등 프론트엔드 파라미터

백엔드(루프 클로저)는 정상 작동 중이므로 `loop_match_*` 는 건드리지 말 것.

## 저속 캘리브레이션 주행 (yaw 스케일 구하기)

정상 주행 데이터로는 계통 성분을 깨끗하게 못 뽑는다. 슬립이 섞여 있어서
run1의 "4.6%" 도 대략적인 크기일 뿐이다. **슬립은 속도와 횡가속도에
비례하므로, 천천히 돌면 비계통 성분이 사라지고 계통 성분만 남는다.**

### 절차

1. **걷는 속도로** 트랙 2~3바퀴. 급가속·급제동·급조향 없이 일정하게.
   랩 수를 정확히 세어둘 것 (참값 계산에 필요)
2. 같은 로거로 기록
   ```bash
   python3 map_odom_log.py calib_slow.csv base_link
   ```
3. ```bash
   python3 analyze2.py calib_slow.csv
   ```
4. **`osc_rms` 가 2~3도 이하인지 먼저 확인.** 여기서 크면 아직 슬립이
   섞인 것이니 더 천천히 다시 돈다. 이 조건이 안 맞으면 아래 숫자는 무의미하다

### 계산

`analyze2.py` 가 찍는 누적 헤딩을 쓴다.

```
scale = (랩수 × 360) / 누적_헤딩_odom
```

run1 예시라면 `1080 / 1043.6 = 1.035`. 오도메트리가 회전을 3.5% 적게 센다.

### 적용

VESC 오도메트리가 `yaw_rate = v·tan(δ) / L` 로 계산된다면 둘 중 하나:

```
L_new     = L_old / scale        # wheelbase 를 scale 만큼 줄인다
steer_gain_new = steer_gain_old * scale   # 또는 조향 게인을 키운다
```

둘 다 하면 안 된다. 하나만 고른다.

### 검증

같은 저속 주행을 다시 뜨고 `trend` 가 0 근처(±0.1 deg/s)로 내려왔는지 본다.
부호가 뒤집혔으면 과보정이니 scale 을 되돌려 절반만 적용한다.

### 이동거리 스케일은 별도

이 도구로는 판정할 수 없다 (아래 "알려진 한계" 참고). 필요하면 따로 잰다:

1. 줄자로 직선 10 m 를 표시
2. 저속으로 직진 주행하며 로거 기록
3. `analyze.py` 의 `path length odom` 과 10 m 를 비교
4. 어긋나면 휠 반지름 / 기어비 파라미터를 그 비율로 보정

## 대회장에서

노면이 바뀌면 **비계통 성분(슬립)이 통째로 달라진다.** 연습실에서 맞춘
값이 대회장 카펫에서 그대로 맞을 거라고 가정하면 안 된다. 도착하면
연습 주행 2~3랩 돌리면서 로거를 띄워 `osc_rms` 를 다시 재고,
run1(rms 9.2도)과 비교할 것.

반대로 **계통 성분(추세)은 노면과 무관**하다. 차량 기하 문제이므로
한 번 맞춰두면 대회장에서 다시 안 잡아도 된다.

매핑 주행 전 30초 점검용으로도 쓸 수 있다:

- 로거가 `rows` 를 못 세면 → TF 체인이 끊긴 것 (`/tf_static` 부터 확인)
- `trend`, `osc_rms` 가 연습 때와 크게 다르면 → 매핑 돌리기 전에 원인부터

랩 검출은 출발점 1 m 이내 복귀로 판정한다. 트랙이 닫힌 루프여야
`analyze2.py` 의 "참값 = 랩수 × 360도" 비교가 성립한다.

## 알려진 한계

`analyze2.py` 의 per-sample 회귀 스케일(1.046)은 **신뢰하지 말 것.**
`lookup_transform` 을 체인별로 따로 최신값 조회해서 `map->base` 가
`odom->base` 보다 한 스텝 늦게 잡힌다. 보정값이 안 변한 프레임에서
두 경로길이가 같아야 하는데 1.165배로 나오는 것이 그 증거다.

신뢰 가능한 값은 SLAM이 직접 발행한 `map->odom` 관측치와 누적 헤딩뿐이다.
같은 이유로 **이동거리 스케일 오차는 이 데이터로 판정할 수 없다.**
